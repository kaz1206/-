## P4 の目的（これだけ）

> 最適化ラウンドの全パスに、**明らかに不適格な候補を安価なルールで落とす「足切り」**をかけ、**すべてのゲートの結果と理由を記録**する。`rlab why-not <candidate_id>` で、どのゲートで、どの値が、どの閾値に対して落ちたかを全部表示できる状態にする。

P4 はランキングも選抜もしない（§3.3「やらないこと」）。P4 を通っても「良い候補」ではなく、「次の評価（P5 ロバストネス・P6 統計）に進める資格がある」という意味にとどまる。

## 1. 調査結果（計画の根拠）

### 1.1 PSR・MinTRL の一次情報（2026-10-11 に確認）

| 事項 | 内容 | 確認レベル |
|---|---|---|
| PSR の式 | PSR(SR*) = Φ( (ŜR − SR*)·√(n−1) / √(1 − γ̂₃·ŜR + (γ̂₄−1)/4·ŜR²) )。ŜR は年率化しない観測頻度の Sharpe（標本標準偏差）、γ̂₃ は歪度、γ̂₄ は**超過でない**尖度（moment 法） | **A**（R PerformanceAnalytics 2.1.0 `ProbSharpeRatio.R` のソースで確認。設計書の式 [S-PSR] と一致） |
| MinTRL の式 | MinTRL = 1 + (1 − γ̂₃·ŜR + (γ̂₄−1)/4·ŜR²)·(z_p / (ŜR − SR*))² | **A**（同 `MinTRL.R`） |
| R の既定値 | **`ignore_kurtosis = TRUE`（尖度を 3 に固定）**、`ignore_skewness = FALSE`。ソースのコメントに「高次モーメントはデータを多く必要とし、短い系列では尖度を使うべきでない」 | A |
| 原著の数値例 | R の例 `sr = 2/√12, refSR = 1/√12, sk = −0.72, kr = 5.78, n = 59`（月次）。原著の掲載値そのものは今回確認できず | 例の入力は A、原著の出力値は未確認 |

→ 設計どおり**原著の式（尖度を含む）**を使う。日次データで 1 年あたり約 260 点あり、R の注意書き（短い系列）には当たりにくい。尖度が大きいほど PSR は下がる（＝保守側）。R と比べるテストでは `ignore_kurtosis = FALSE` に相当する値と比べる（M1）。

### 1.2 既存実装の評価（CLAUDE.md の 5 観点）

| 候補 | 評価 | 採否 |
|---|---|---|
| R PerformanceAnalytics | 式の参照実装として最良（CRAN、2026-04 更新）。ただし Python から呼ぶには R が必要 | **検算の基準**（テストオラクル）に使う。依存には入れない |
| Python の既存パッケージ（quantstats など） | 式は数行で、パッケージごとに尖度の定義（超過かどうか）や既定値がばらつく。依存を増やす価値がない | 不採用 |
| 自前実装 | 式は数行。scipy の `norm.cdf` / `norm.ppf` を使う。P2 で尖度（`fisher=False`）・歪度（`bias=True`）はすでに R の moment 法と同じ定義で計算している | **採用** |

依存関係（レビュー指摘 ③ の確認）: SciPy は **P2 から依存に入っている**（`pyproject.toml` に `scipy>=1.16`、`uv.lock` で 1.18.1 に固定、`metrics/engine.py` で使用中）。`uv sync` は件数しか表示しないので一覧には出ない。P4 で依存の追加は不要だが、`scipy.stats.norm` を使うことをテストで直接確認し、新しい依存を足す場合は `pyproject.toml` と `uv.lock` の更新を変更ファイルに含める。

### 1.3 P3 のデータで分かっていること

1,044 パスの純損益の中央値は −20.56、黒字は 32%（P3_PLAN §12）。動作確認用の EA にエッジはないはずなので、**P4 を通るパスはほぼない**と予想する。これはそのまま「フィルタが機能しているか」の最初の確認になる。

ただし、**PSR は多重検定を補正しない**。エッジのない 1,044 パスに PSR ≥ 0.95 をかけると、偶然でも約 5%（50 前後）が通りうる。これを割り引くのは P6 の DSR（試行回数 N = 1,044 を使う）の役割で、P4 では補正しない。この役割分担を設計どおり守る。

- MinTRL は判定に使わず、「あと何日あれば PSR が閾値に届くか」として `why-not` に表示する（§9.6 の設計どおり）。
- 値が計算できないとき（null）は、その理由（例: `zero variance`）を記録し、**合格扱いにしない**。

### 3.2 DD の上限ゲートを P4 に入れない理由（M2、設計変更）

設計書 §3.3 は足切りの例に「DD 上限超過」を挙げている。しかし本基盤は**固定ロット（0.01）で研究し、ロットは P9 の資金配分で決める**（§12.1）。そのため、P4 時点の DD 金額や DD% はロットと初期資金の置き方しだいでいくらでも変わる。0.01 ロットの DD% で足切りをすると、閾値の意味がなくなる。

→ P4 では**ロットに依存しない基準**（破産・ロスカット・証拠金・PSR・期待値・取引数）だけで足切りする。DD のリスクは P9 で、モンテカルロにより「配分後のロットで DD が上限を超える確率」として評価する。DD の値は P4 でも記録し、`why-not` に表示する。

### 3.3 証拠金維持率の前提（レビュー指摘 ①、M7）

証拠金維持率も、DD と同じく**ロット・初期資金・レバレッジ・ブローカーの証拠金ルール**に依存する。それでも P4 に残す理由と、その条件:

- **同じラウンドの中では条件がそろっている**: 全パスが同じロット（固定値）・初期資金・レバレッジ・銘柄・サーバで実行される（ラウンドのテスター設定で固定済み）。比べる意味があるのは、この中だけ。
- **ポジションを積み増す戦略（グリッド・ナンピン）を見つける目的**: 同時ポジション数が増えると維持率が下がる。これはロットではなく戦略の振る舞いで決まる。
- **条件を判定と一緒に記録する**: 判定の `details_json` に、ロット・初期資金・口座通貨・レバレッジ・銘柄の証拠金計算方式（`account_margin_mode`）・サーバ名を記録する。条件が違うラウンドどうしで維持率の数字を比べない。
- **安全性の判断には使わない**: 200% を下回らなかったことは「配分後も安全」を意味しない。実際のロットでの証拠金の安全性は、P9 で `order_calc_margin`（MetaTrader5 Python API、採用済みの既存実装）を使って評価し直す。
- 文書と `why-not` の表示では「ラウンドの標準条件（例: 0.01 ロット・10,000 USD・100 倍）での最小証拠金維持率」と書き、条件を省いた「維持率 200% 以上＝安全」という表現をしない。

なお、PSR は日次リターンの平均と標準偏差の比なので、**ロットを何倍にしても値が変わらない**（両方が同じ倍率で変わる）。DD や証拠金維持率と違い、ロットに依存しない基準である。

### 3.4 PSR の入力データの定義（レビュー指摘 ②）

PSR に入れるデータを次のとおり固定する。P2（m2/m3）と P3（p1）で使っている定義と同じで、`docs/metrics_definitions.md` の「日次系列」に従う。

| 項目 | 定義 |
|---|---|
| 1 日の区切り | ブローカーのサーバ時刻の日付。**その日に 1 ティック以上あった日だけ**を 1 日と数える（土日・休場日は行がない） |
| 日次の値 | その日の最後のティック時点の**エクイティ**（含み損益を含む）。最終日は、テスト終了時の強制決済後の値 |
| 日次損益 | **前日の日末エクイティとの差分** E_t − E_{t−1}（初日は E_1 − D）。決済損益と含み損益の変化の両方を含む |
| 日次リターン | **(E_t − E_{t−1}) ÷ D**。分母は初期資金 D で一定（前日のエクイティでは割らない。固定ロット・複利なしの前提、ARCHITECTURE §12.1）。式と理由は表の下 |
| 取引のない日 | ティックがあれば 1 日として含める。ポジションがなければ E_t = E_{t−1} なのでリターンは 0。保有中なら同じ式で、含み損益の変化がそのままリターンになる（別の式は使わない） |
| 期間 | ラウンドの期間 [from, to)（Discovery 期間）。サブ期間には分けない |
| Sharpe | 日次リターンの平均 ÷ **標本標準偏差（ddof = 1）**。**年率化しない**。無リスク金利は 0 |
| 歪度・尖度 | `scipy.stats.skew(bias=True)`、`scipy.stats.kurtosis(fisher=False, bias=True)`（moment 法、尖度は超過でない）。R の `skewness` / `kurtosis(method="moment")` と同じ定義 |
| 標本長 n | 上の日数 |
| 無効値 | 日数 < 2、標準偏差 = 0（取引なしを含む）、歪度・尖度が計算できない、値が NaN・無限大、の場合は PSR を null とし、理由を記録して**不合格**（`LOW_PSR`）。合格扱いにはしない |
| PSR の分母 | 1 − γ̂₃·ŜR + (γ̂₄−1)/4·ŜR² が 0 以下になる場合（理論上は起こりにくい）も null・不合格 |

**計算式（実装そのもの）**: 日 t（t = 1, …, n）の日末エクイティを E_t、初期資金を D、E_0 = D とすると

```
r_t = (E_t − E_{t−1}) / D
```

- **分子 = 前日の日末エクイティとの差分**（決済損益と含み損益の変化を両方含む。「日次損益」はこの差分のことを指す）
- **分母 = 初期資金 D（期間中ずっと一定）**。前日のエクイティ E_{t−1} では割らない
- 初日は E_0 = D との差分
- 実装: `metrics/engine.py` の `daily_metrics`（`np.diff([D, E_1, …, E_n]) / D`）。P2・P3 と同じコードを使う

例: D = 10,000、E_1 = 10,012、E_2 = 10,003 なら r_1 = +12 / 10,000 = +0.0012、r_2 = −9 / 10,000 = −0.0009。

複利型の r_t = E_t / E_{t−1} − 1 は**使わない**。理由: 固定ロットでは損益の大きさがエクイティに比例しないので、分母を動かすと、同じ損益でも残高が減った後ほどリターンが大きく見える歪みが出る。分母を一定にすると、Σ r_t = 純損益 / D になり、ロットを k 倍すると全ての r_t が k 倍になるだけなので Sharpe・PSR は変わらない。ストラテジーテスターでは期間中の入出金がない（入金は開始時の 1 回だけ）ので、E_t の変化はすべて取引によるもの。

この定義を `docs/metrics_definitions.md` に「PSR の入力」として追記し、PSR の評価値と一緒に定義のバージョンを記録する。

### 3.5 PSR の閾値の意味（レビュー指摘 ④）

- PSR(SR*) は「推定に使った仮定（漸近正規近似、リターンの系列相関が弱いこと）のもとで、**真の Sharpe が基準 SR* を上回ることを、観測データがどの程度支持するか**」を表す値。
- **PSR 0.95 は「将来 95% の確率で利益が出る」という意味ではない。** P4 の通過は将来の利益を保証しない。
- 形式上は片側検定の「1 − p 値」にあたるが、日次リターンの系列相関・非定常性、そして**多数の試行から選んでいること**（多重検定）を考えると、古典的な「片側 5% 有意」と無条件に同一視はしない。
- 文書と CLI では「基準 Sharpe（SR* = 0）を上回ることを支持する PSR の閾値 0.95」と表現する。多重検定の補正は P6 の DSR で行う。

### 3.6 判定の再現性

- 判定は「ラウンド × プロファイルの内容ハッシュ × ゲートの実装バージョン」で一意に決まる。同じ組み合わせで再実行したら既存の結果を返す（冪等）。
- プロファイルの閾値を変えると、新しいフィルタ実行として**別に記録**する（古い判定は消さない）。閾値の変更回数は「研究者の自由度」なので、`filter show` に同じラウンドへの実行回数を表示する（§10.4 の考え方）。

| ゲートの網羅性 | **最初のゲート（破産など）で落ちても、残りの全ゲートが評価・保存される**。理由コードが複数つく |
| 再現性 | **同じラウンド・同じプロファイルなら既存の結果を返す。閾値を変えたら別の判定として保存**され、古い判定は残る。同じラウンドへの実行回数が表示される |
| 証拠金の条件 | 判定にロット・初期資金・レバレッジ・証拠金計算方式・サーバが記録される |
| DB 移行 | **P3 までの既存データ（v3）を壊さずに v4 へ移行**できる（行数・内容が変わらない） |
| 依存 | `scipy.stats.norm` が使えること（`uv.lock` で固定された版） |
| ストレージ（M4） | 新形式で保存され、正規化 CSV のハッシュで再現性の比較ができる |

## 8. 承認をお願いしたい判断（要約）

| ID | 判断 | 推奨 | 理由 |
|---|---|---|---|
| M1 | PSR は原著の式（尖度を含む）を使う。R の既定値（尖度を無視）とは違うことを明記する | 原著の式 | 設計（§10.2）どおり。日次データは十分な長さがあり、裾が厚いほど PSR が下がる＝保守側 |
| M2 | DD の上限による足切りを P4 から外し、P9（配分後のロットでのモンテカルロ）で評価する | 外す | 固定ロットの DD% はロットしだいで意味が変わる。DD の値は記録・表示はする |
| M3 | P4 の対象は最適化ラウンドの全パスに限る（単一テストは P8 で扱う） | そのとおり | P4 の目的は「大量の試行の足切り」。単一テストは検証段階でまとめて扱う |
| M4 | 日次データの保存を「Parquet が正本、生 CSV は gzip、正規化 CSV はハッシュのみ」に変える | 変える | 保存量を約 1/5〜1/10 に。再現性の比較方法（E1）は変えない |
| M5 | 既定の閾値: PSR ≥ 0.95（SR* = 0）、取引数の下限 30、日次データ 60 日以上、証拠金維持率 200% 以上 | この値 | PSR 0.95 は片側 5% 有意に相当する慣例。30 と 60 は推定の安全装置（本体は PSR）。200% は一般的なマージンコール水準（100%）に余裕を持たせた値。いずれもプロファイルで変更でき、変更は記録される |
| M6 | 取引頻度がプロファイルの想定外でも、足切りせず警告（WARN）にとどめる | WARN | 頻度は戦略の性格の手がかりで、合否の根拠としては弱い |
| M7 | 証拠金維持率のゲートは「ラウンドの標準条件での値」として残し、条件（ロット・初期資金・レバレッジ・証拠金計算方式・サーバ）を判定に記録する。安全性の判断は P9 で実ロットにより行う（レビュー指摘 ①） | そのとおり | ラウンド内は条件がそろっていて比較でき、ポジションの積み増しを見つけるのに役立つ。条件を省いた数字だけの判断はしない |
| M8 | PSR の入力を §3.4 の定義（エクイティ基準の日次リターン ÷ 初期資金、ティックのある日、標本標準偏差、年率化なし、無効値は不合格）に固定する（レビュー指摘 ②） | そのとおり | P2/P3 の定義と同じ。評価対象が候補ごとにずれないようにする |
| M9 | PSR の閾値の説明を「基準 Sharpe を上回ることを支持する PSR の閾値」とし、利益の確率や古典的な有意水準と同一視しない（レビュー指摘 ④） | そのとおり | P4 通過を将来の利益保証と誤解させないため |

## 9. 実装メモ（計画からの細部の補足）

- **プロファイルの指定方法**: 計画では戦略 YAML に `profile:` を書く予定だったが、最適化ラウンドには「どの戦略 YAML から作ったか」が記録されていないので、フィルタ実行時に読みに行けない。そこで `rlab filter run <round_id> --profile intraday` で**明示的に指定**する方式にした（使われない設定項目は混乱のもとなので、戦略 YAML には追加しない）。指定したプロファイルの名前と内容のハッシュは判定ごとに記録される
- **証拠金計算方式（C52）**: 最適化の出力（Frames・XML・テスターログ）には口座の証拠金計算方式が含まれない。判定の条件には `account_margin_mode: null` と、その理由の注記を記録した。サーバ名は XML の `<Server>` から取る
- **値が欠けたときの扱い**: どのゲートでも、必要な値が欠けている・数値でない・有限でない場合は不合格（そのゲートの理由コード＋「missing or not finite」の注記）。例外は証拠金維持率で、ポジションを一度も持たなかった場合の null は「該当なし」（NOT_APPLICABLE）とする（取引なしのパスは取引数・期待値・PSR で必ず落ちる）
- **対象のジョブ**: 全チャンクに成功ジョブがあるラウンドだけを対象にし、各チャンクの最新の成功ジョブを使う。未完了のラウンドは `ROUND_NOT_READY` で拒否する
- **フィルタ ID**: ラウンド・プロファイルの内容ハッシュ・フィルタの版（`f1`）・入力ジョブの組から決まる。同じなら既存の結果を返す。ラウンドを `--rerun` して入力ジョブが変われば、新しい実行になる
- **C55（ストレージ）**: 正規化 CSV のハッシュは行ごとに計算する（全体を作らない）。テストで、P3 の方式（ファイル全体の sha256）と同じ値になることを確認した。gzip は時刻を 0 に固定して、同じ内容なら同じバイト列になるようにした
- **テスト**: 208 件（P4 で 67 件追加）。R の例（`sr = 2/√12, refSR = 1/√12, sk = −0.72, kr = 5.78, n = 59`）で PSR ≈ 0.9487、MinTRL ≈ 59.90（n = 59 ではわずかに 0.95 に届かず、60 で届く）
