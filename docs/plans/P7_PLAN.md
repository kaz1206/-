# P7 実装計画: 候補の判定と選抜（Selection）

- 状態: **計画（承認待ち、第 1 版）**
- 作成日: 2026-10-11
- 前提: P6 完了（`docs/plans/P6_PLAN.md` §11）。設計書 `docs/ARCHITECTURE.md` §3.6・§5.4・§6.2・§11・§19.4・§21.2-3・§21.3、§20「P7 選択」
- 進め方: **計画 → 承認 → 実装 → 実データで動作確認**。MT5 は使わない

## P7 の目的（これだけ）

> P4（足切り）・P5（ロバストネス）・P6（統計）の結果をまとめて、候補ごとに「次の段階（P8: 新しい期間での検証）へ進めるか」を**理由コード付きで判定**し、進める候補を**上限数（予算）以内**で選ぶ。

P7 は**合否と選抜を決める最初の段階**です。ここで決めた候補だけが P8 に進みます。P7 で使うのは Discovery 期間（候補を選んだ期間）の値だけで、P7 の判定は「将来も儲かる」ことの証拠ではありません（§5）。

## 3. 判定と選抜の仕様案

### 3.1 全体の流れ（設計書 §11.3 の推奨構成を、今使えるデータに合わせたもの）

```
P4 合格の候補（それ以外は P7 の対象外。件数だけ表示）
  → ① ゲート（合否、理由コード付き）: 孤立したピーク・近傍の不安定
  → ② 領域ごとに代表を 1 つ（メドイド。メドイドが不合格なら、合格した中でメドイドに最も近い候補）
  → ③ パレート（非劣解）で並べる: Robust Score ↑、保守的な DSR ↑、再標本化した最大 DD の 95% 点 ↓
  → ④ 予算 K（既定 5）まで、前の層から順に採る
  → SELECTED / NOT_SELECTED（理由: REDUNDANT_IN_REGION・DOMINATED・NOT_SELECTED_BUDGET）/ FAIL（ゲートの理由）
```

### 3.2 ゲート（① 合否を決めるもの）

| ゲート | 理由コード | 条件（不合格） | 既定値 | 根拠 |
|---|---|---|---|---|
| 孤立した合格点 | `ISOLATED_PEAK` | P4 合格だが、隣（チェビシェフ距離 1）に P4 合格が 1 つもない（P5 の `region_status = ISOLATED_PASS`） | — | 設計書 §9.3・§11.3（領域の代表だけを選ぶ） |
| 孤立したピーク | `ISOLATED_PEAK` | Peak Ratio（自分 ÷ 近傍の中央値）> 1.5 | 1.5 | 設計書 §9.2 の例示値 |
| 近傍の不安定 | `NEIGHBORHOOD_UNSTABLE` | 近傍（自分を含む）の 25% 分位点（Robust Score）≤ 0、または近傍に破産・ロスカットがある | 0 | 「周りが悪い」＝少しずれると負ける。破産が隣にある設定は危険（設計書 §9.2） |

**R3（判断をお願いしたい点）: 近傍に「取引なし」がある場合の扱い**
- P5 の Robust Score は、近傍に取引なし（NO_TRADES）が 1 つでもあると −∞ 扱いの影響を受け、「計算できない」になりやすい。P3 の EA のように、短期 ≥ 長期の組合せを「取引しないパス」として走らせる EA では、その境目にある候補が**近傍の『取引なし』のせいだけで**不合格になる
- 案: P7 のゲートでは、近傍の NO_TRADES を「グリッドの外」と同じ扱い（数えない）にして Robust Score を計算し直す。破産・ロスカット（BANKRUPTCY / STOP_OUT）は従来どおり −∞（不合格の方向）。数え直した近傍が全体の半分未満なら警告 `EDGE`。**独自拡張**として、P5 の値と並べて記録する
- 理由: 「取引しない」は損失ではなく「その設定では何もしない」。破産とは意味が違う（P5 の C59 で原因を分けて記録したのはこのため）

### 3.3 警告（記録するが合否には使わない）

| 警告コード | 条件 | 出どころ |
|---|---|---|
| `LOW_DSR` | 保守的な DSR < 0.95 | P6 |
| `SERIAL_DEPENDENCE_HIGH` | n / n* ≥ 1.5 | P6 |
| `SHARPE_CI_INCLUDES_ZERO` | ブートストラップの Sharpe 90% 区間が 0 を含む | P6 |
| `BOOTSTRAP_SENSITIVITY` | 循環ブロックと定常ブートストラップの区間幅が大きく違う | P6 |
| `EDGE` | 近傍が全体の半分未満（グリッドの端、または取引なしに囲まれている） | P5 / R3 |
| `SUBPERIOD_INCONSISTENT` | 黒字の年の割合 < 0.5、または最悪年がマイナス | P5（2 年分しかないので、合否には使わない） |
| `TRADE_FREQUENCY_OUT_OF_PROFILE` | P4 の警告を引き継ぐ | P4 |

### 3.4 DSR の使い方（P6 承認条件 1 を守る仕組み）

- DSR はゲートに使わない。`LOW_DSR` は警告コードだけに入り、**理由コード（`reason_codes`）には入らない**
- パレート（③）では、DSR は 3 つの物差しの 1 つ。ある候補が「DSR だけで」落ちることはない（**他の 2 つで同等以上かつ DSR で上回る候補がある**ときにだけ後ろの層になる＝相対的な順位づけ）。閾値（例: 0.95 以上）として使うことはしない
- テストで保証: 全判定の `reason_codes` に DSR 由来のコードがないこと。DSR の値だけを変えても FAIL / PASS が変わらないこと（SELECTED と NOT_SELECTED の入れ替わりは起こりうる＝順位づけ）

**R4（判断をお願いしたい点）**: 上の「パレートの物差しに DSR を入れる」案（推奨）と、「DSR はパレートに入れず、表示の並び順と警告だけに使う」案のどちらにするか。
- 推奨案の理由: 設計書 §11.2 の既定。選択による上振れを補正した値を並べ方に使わないと、偶然高く出た候補を優先しやすい
- 代替案の利点: DSR が選抜結果に影響しないので、P6 の既知の限界（AR(2) など）の影響を受けない

### 3.5 パレートと予算（③④）

| 項目 | 案 | 理由 |
|---|---|---|
| 物差し | Robust Score（↑）、保守的な DSR（↑）、再標本化した最大 DD の 95% 点（日末、口座通貨、↓） | 設計書 §11.2。指標を増やすこと自体が多重検定（§21.2-3）なので 3 つに絞る。コスト感度は P8 へ（C60） |
| 最大 DD を金額で比べてよいか | 同じラウンドの中ではロット・初期資金が同じなので比べられる。ラウンドをまたいで比べない（P7 はラウンド単位） | C51（DD の上限は P9） |
| 層の作り方 | 非劣解の層（第 1 層 = どの候補にも負けていない候補、第 2 層 = 第 1 層を除いて負けていない候補 …）。O(n²) の単純な比較で実装 | 候補は多くても数百。既存ライブラリ（pymoo 0.6.2 は依存が多い、paretoset 1.2.5 は numba・pandas が必要）を入れるほどではない |
| 予算を超えたとき | 前の層から順に採り、最後の層だけは Robust Score の高い順（同点は candidate_id の辞書順）で埋める | 設計書は「混雑距離」（NSGA-II）。混雑距離は物差しの空間での多様性で、**パラメータの多様性は ② の領域代表ですでに確保している**。単純・決定的な方を選ぶ（設計変更 C68 として記録） |
| 予算 K | 全体 5、同じ領域から 1 | P8 では候補ごとに複数の期間で単一テストを行うので、実行コストと、検証段階の多重検定の負荷を抑える |
| 理由コード | 領域の代表でない → `REDUNDANT_IN_REGION`。選ばれた候補のどれかに負けている → `DOMINATED`。それ以外で予算外 → `NOT_SELECTED_BUDGET` | 設計書 §5.4 |

### 3.6 事前登録と「選び直し」の記録（設計書 §11.4）

- 閾値・予算・物差し・Selector 名は `configs/selection_profiles.yaml`（新規）に置き、内容のハッシュを判定に記録する。値を変えると別の実行として記録され、古い判定は書き換えない
- 同じラウンドで、**違う設定・違う Selector で選び直した回数**を数えて表示し、2 回目以降には警告 `SELECTION_REVISED` を付ける。P8 では、どの選抜結果を使ったかを記録する（P8 の計画で扱う）
- Selector は既定の 1 種類（`region_pareto_v1`）だけを CLI から使えるようにする。比較用の単純な Selector（P4 合格を Robust Score 順に上位 K、`hard_gate_v1`）はベンチマーク（§6）の中だけで使う。**選択肢を増やすこと自体が Selector の過学習を招く**（設計書 §21.3）

## 5. データの独立性（P8 と混同しない）

- P7 が読むのは、そのラウンドの FILTER（P4）・ROBUSTNESS（P5）・STATISTICS（P6）の評価値だけ。どれも Discovery 期間の値
- 設計書 §6.2 の※1: P8 の検証結果を P7 の選抜に戻すと、検証期間もイン・サンプルになる。P8 で落ちた候補の代わりに P7 の次点を繰り上げることは、**新しい選抜として記録**し（`SELECTION_REVISED`）、P8 の計画で回数を数える
- 表示に「Discovery 期間の値で選んだ結果で、将来の成績の予測ではない」と注記する

## 6. テスト

### 6.1 合成グリッドでの Selector のベンチマーク（設計書 §19.4、合格基準は事前に固定）

30 × 30 のグリッドに、なめらかなノイズ（相関のある偶然の山）を置き、条件ごとに 500 回（シード 20261011）。

| シナリオ | 内容 | 合格基準（事前に固定） | 実装前の試算（500 回） |
|---|---|---|---|
| A: 本物の台地 ＋ 偶然の尖り | 6 × 6 の台地（真のスコア +0.08）と、孤立した尖り 3 つ（0.15） | `region_pareto_v1` が台地の候補を選ぶ割合の 95% 下限 ≥ 90%、尖りを選ぶ割合の 95% 上限 ≤ 5% | 台地 100%、尖り 0% |
| A の比較 | 素朴な方法（生のスコア最大の 1 点）・`hard_gate_v1` | 記録のみ | 素朴な方法は **99.8% で尖りを選ぶ**。`hard_gate_v1` は台地 99.6%・尖り 0% |
| B: 尖りだけ（台地なし） | 偶然の山と尖り 3 つ | 尖りを選ぶ割合の 95% 上限 ≤ 5% | 0%（`hard_gate_v1` は **45%** で尖りを選ぶ） |
| C: ノイズだけ | 偶然の山だけ | 記録のみ（パイプライン全体の偶然の合格率は P10 で測る） | **73% の回で何かが選ばれる**（平均 1.1 件） |

試算の条件: P4 の合格を「スコア > 0.05」、DSR を「スコアの大きさ」、最大 DD を乱数で代用した簡易版（`docs/research/p7_simulations/proto.py`）。実装後は本番の関数で同じ実験をテストとして書き直す。

**試算から分かったこと（大事）**:
- 領域の代表を選ぶ方法は、**孤立した尖り（偶然の当たり）を確実に避ける**。生のスコアで最大の 1 点を選ぶ（MT5 の最適化結果を上から選ぶ）と、ほぼ必ず尖りを選んでしまう
- 一方で、**なめらかな偶然の山（隣どうしが似た成績になるノイズ）は、本物の台地と区別できない**（C で 73%）。最適化のパスは隣どうしが強く相関しているので、偶然でも「台地のような形」ができる。P7 の選抜は「孤立した偶然」を落とすだけで、「広がりのある偶然」は落とせない
- したがって **P7 で選ばれたことは、エッジがある証拠ではない**。広がりのある偶然を落とすのは P8（新しい期間で同じパラメータを試す）と P10（パイプライン全体の偶然の合格率）の役割。この限界を P7 の表示と結果に明記する

### 6.2 そのほかのテスト

| テスト | 期待 |
|---|---|
| 決定性 | 入力の並び順を変えても、選ばれる候補・順位・ID が完全に同じ |
| 予算 | 選ばれるのは K 件以下、同じ領域から 1 件以下 |
| DSR が合否を決めない | `reason_codes` に DSR 由来のコードがない。DSR だけを変えても FAIL / PASS が変わらない |
| ゲート | 孤立した合格点・Peak Ratio > 1.5・Robust Score ≤ 0・隣の破産が、それぞれ正しい理由コードで落ちる。R3 の取引なしの扱い |
| 代表の選び方 | メドイドが不合格のとき、合格した中で最も近い候補が代表になる |
| 入力の検査 | ラウンド違い・ブートストラップ不足・Discovery 以外の評価値を拒否 |
| 合格 0 件 | P4 合格 0 件のとき、選抜 0 件・理由 `NO_ELIGIBLE` で正常終了 |
| 冪等・選び直し | 同じ入力の再実行は ALREADY_DONE。設定を変えると別の実行になり `SELECTION_REVISED` |
| 全体の流れ（偽の端末） | P4 合格が出るように調整した合成ラウンドで、足切り → ロバストネス → 統計 → 選抜まで通す |
| P0〜P6 | 既存のテストがすべて通る |
