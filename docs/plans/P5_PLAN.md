# P5 実装計画: ロバストネス評価（パラメータの島の数値化）

- 状態: **完了（2026-10-11、実機のデータで動作確認済み）**。結果は §11。承認: N1〜N9（C56〜C60）
- 作成日: 2026-10-11
- 前提: P4 完了（`docs/plans/P4_PLAN.md` §11）。設計書 `docs/ARCHITECTURE.md` §3.4（Robustness Evaluation）、§9（ロバストネス評価設計）、§20「P5 ロバストネス」
- 進め方: **計画 → 承認 → 実装 → 実機のデータで動作確認**。MT5 は使わない（P3 で保存した全パスの指標と日次データだけを読む）

## P5 の目的（これだけ）

> MT5 の 3D 表示で目で見ていた「パラメータの島」を、**近傍の統計で数値化**し、「頂上は高いが周りが崖」の候補（孤立ピーク）と「周りも高い台地」の候補を区別できるようにする。

設計書 §3.4 のとおり、P5 は**評価値を出すだけで合否は決めない**（判定は P7 の選抜で使う）。

## 1. 調査結果（計画の根拠）

### 1.1 既存実装の確認（SciPy 1.18.1。`uv.lock` で固定した版の docstring と実際の動作で確認）

`docs.scipy.org` にはこの環境から接続できなかったので、プロジェクトで固定している版そのものの docstring と動作で確認した（固定版の実物なので確認レベル A）。

| 関数 | 確認したこと | 本基盤での使い方 |
|---|---|---|
| `scipy.ndimage.generic_filter(input, function, footprint=…, mode=…, cval=…)` | 窓内の値を関数に渡す。**既定の `mode='reflect'` は端の外側を鏡写しの値で埋める** | `mode='constant', cval=NaN` で端の外側を NaN にし、NaN を無視する関数（下記）で近傍の統計を計算。**鏡写しは端の点の近傍を水増しするので使わない** |
| `scipy.ndimage.label(input, structure=…)` | **既定の連結は「上下左右だけ」**（2 次元で 4 近傍） | `structure=generate_binary_structure(d, d)` で斜めも含む連結にする（近傍の定義 §9.1 のチェビシェフ距離 1 と一致させる）。斜めにつながった点が 1 つの島になることを実際に確認した |
| `scipy.ndimage.percentile_filter` | NaN を無視しない | 使わない（端の扱いができないため） |
| `numpy.nanpercentile(…, method=…)` | **既定の `linear` 補間は、−∞ が混ざると NaN を返す**（実際に確認）。`inverted_cdf`（補間しない順序統計量）は −∞ を正しく扱う | `method="inverted_cdf"` を使い、評価値と一緒に記録する |

→ 近傍の計算・島の検出は SciPy の既存関数で行い、自前で書くのは「どの関数をどの設定で呼ぶか」だけにする（再発明しない）。

### 1.2 P3・P4 のデータで分かっていること

- 1,044 パスはすべて完全グリッド（36 × 29）上にあるので、**近傍は既存のパスから取れる**（追加の MT5 実行は不要。設計書 §9.1）
- P4 では合格 0 件。P5 の「島」は P4 合格点だけで作る設計（§9.3）なので、**この EA では島は 0 個になる**と予想する。島の検出が正しく働くことは、合成データのテストで確かめる（§6）
- パスごとの約定一覧は保存していない（P3 の設計）。そのため、約定を使う評価（利益集中度、コストの事後計算）は P5 では扱えない（§2.2）

## 3. 指標の仕様案

記号: s(c) = 候補 c のスコア、N(c) = c のチェビシェフ距離 1 の近傍（c 自身は含まない、グリッドの外は含まない）。

| 指標 | 定義 | 解釈 |
|---|---|---|
| **Robust Score** | {s(c)} ∪ {s(n) : n ∈ N(c)} の **25% 分位点**（`inverted_cdf`） | 選抜の主指標。「頂上の高さ」より「足元の固さ」 |
| 近傍数 | \|N(c)\|。2 軸の内側なら 8、辺は 5、角は 3 | 少ないほど統計が不安定 |
| 端フラグ | \|N(c)\| が内側の近傍数の半分未満なら `EDGE` | 角の点などを、選抜で慎重に扱うため |
| Neighbor Pass Rate | N(c) のうち P4 に合格した割合 | 低い＝崖っぷち |
| **Peak Gap**（M2） | s(c) − median{s(n) : n ∈ N(c)} | 大きい＝周りより突き出ている |
| Peak Ratio | s(c) ÷ 近傍の中央値。**中央値が 0 以下のときは計算しない**（null と理由） | 設計書 §9.2 の指標。日次シャープは負にもなるので、比は 0 付近で意味を失う（M2） |
| Plateau Size | c が属する島の点数（島にいなければ 0） | 島の面積 |
| 島の ID・メドイド | 島ごとに、島内の他の点とのチェビシェフ距離の合計が最小の点（同点なら Robust Score が高い方、さらに同点なら座標が小さい方） | 頂上ではなく、島の中心を代表にする |
| 感度（軸ごと） | 軸方向に隣り合う 2 点のスコア差の絶対値の中央値（両方とも有限のときだけ）。ラウンド全体と、候補ごとの最大値 | どのパラメータが効きすぎているか |
| サブ期間の一貫性 | 暦年ごとに Σ r_t（その年の損益 ÷ 初期資金）と日次シャープ。黒字年の割合、最悪年の値、年別シャープの標準偏差 | 特定の年だけで稼いでいないか |

- **島の作り方（M3）**: 島の点 = **P4 に合格した点**。設計書 §9.3 の「スコア ≥ 閾値」は、P4 の PSR ゲートがすでに「日次シャープが十分に高い」ことを確かめているので、新しい閾値を足さない（恣意的なパラメータを増やさないため）
- −∞ の扱い: 分位点・中央値は −∞ を「最低の値」として含める。近傍に −∞ が多い点は Robust Score も −∞ になる（保守側）。**計算の内部では −∞ にまとめるが、保存では原因を区別する**（§3.2、レビュー指摘 1）
- 次元: 軸がいくつでも同じ定義で計算する（近傍は 3^d − 1 点）。軸が 4〜5 個を超えると近傍が大きくなる問題（§9.1）は、完全グリッドの最適化の範囲では計算量の問題にとどまる。感度の低い軸を外す仕組みは将来の課題にする

### 3.2 スコアの状態と、−∞ の原因の記録（レビュー指摘 1、N8）

取引なしと、破産・ロスカットは**同じ状態ではない**（前者は戦略が成立していない可能性、後者は重大なリスク）。計算の内部では保守的に同じ −∞ として扱うが、保存する評価値では原因を別々に残し、後の段階（P7 の選抜、P10 の検証）で区別できるようにする。

**① 候補自身のスコアの状態**（`score_status`。複数当てはまる場合は上から優先して 1 つ、該当するもの全部も `score_flags` に記録）

| コード | 条件 | 意味 | 内部のスコア |
|---|---|---|---|
| `BANKRUPTCY` | 破産（エクイティ ≤ 0） | 重大なリスク | −∞ |
| `STOP_OUT` | ロスカット約定あり | 重大なリスク | −∞ |
| `NO_TRADES` | 取引数 0（日次リターンの分散 0 を含む） | 戦略が成立していない可能性 | −∞ |
| `NOT_COMPUTABLE` | 上記以外で日次シャープが欠けている・有限でない | データの問題 | −∞ |
| `OK` | 日次シャープが計算できた | — | 日次シャープ |

**② 近傍の内訳**（候補ごとに保存）: 近傍の各点の `score_status` を数えた件数（例: `{"OK": 5, "NO_TRADES": 3}`）。Robust Score や Peak Gap が −∞（保存では null）になったとき、**それが「周りに取引しない設定がある」せいなのか、「周りで破産している」せいなのか**を後から区別できる。

**③ 保存の形**: −∞ になった指標は null とし、理由を `*_reason` に入れる。例: `robust_score: null, robust_score_reason: "neighbourhood includes -inf scores: NO_TRADES 3 of 9"`。原因を消した単なる null は保存しない。

### 3.3 島がないことと、周辺が不安定なことを区別する（レビュー指摘 2、N9）

- **Robust Score・Peak Gap・近傍の合格率・感度・年ごとの一貫性は、P4 の合否にかかわらず全候補で計算して保存する**（P4 不合格の候補も含む。§7 の完了条件 2 は「1,044 パスすべて」）。島（Plateau Size・メドイド）だけが P4 合格点を使う
- 候補ごとに、島に入っていない理由を `region_status` として残す:

| コード | 意味 |
|---|---|
| `IN_REGION` | 島に入っている（島の ID・面積・メドイドからの距離を記録） |
| `NOT_FILTER_PASS` | P4 で不合格なので、島の対象外（周辺の安定性は Robust Score などで別に評価済み） |
| `ISOLATED_PASS` | P4 に合格しているが、隣に合格点がない（面積 1 の島） |

- ラウンド全体でも、島が 0 個の理由を `regions_reason` として残す: `NO_FILTER_PASS`（P4 合格が 0 件。今回の予想）と、`ALL_ISOLATED`（合格点はあるが、すべて孤立）を区別する
- これにより「島がない」ことが「周辺の成績が不安定」と同じ意味に読まれない。周辺の安定性は、島の有無ではなく Robust Score などの値で読む

### 3.4 独自拡張の明示（CLAUDE.md の約束）

| 項目 | 標準（設計書 §9.2・§9.3） | 本計画 | 種類 |
|---|---|---|---|
| Peak Ratio | 比のみ | 中央値 ≤ 0 なら計算しない。差（Peak Gap）を併記 | **独自拡張**（負になりうるスコアへの対応） |
| 島の条件 | フィルタ PASS かつスコア ≥ 閾値 | フィルタ PASS のみ（PSR が閾値の役割） | 設計の具体化 |
| 端の扱い | 記載なし | 近傍数を記録し、半分未満に `EDGE` フラグ | 設計の具体化 |

## 8. 承認をお願いしたい判断（要約）

| ID | 判断 | 推奨 | 理由 |

| N1 | スコアは日次シャープ（年率化なし）。計算できないパス・取引なし・破産・ロスカットは、計算の内部では −∞（原因の記録は N8） | そのとおり | 設計書 §9.2 の既定。PF や純利益は単独のスコアにしない。近くの設定で取引が止まる・破産するのは、どちらも挙動の不連続（崖）として保守的に扱う |

## 9. 実装メモ（計画からの細部の補足）

- **CLI**: `rlab robust run <round_id> --filter <filter_id>`（フィルタ実行が別のラウンドのものなら `FILTER_ROUND_MISMATCH` で拒否）、`rlab robust show <robust_id> [--candidate <cd>]`、`rlab robust map <robust_id> [--metric score|robust]`
- **地図の記号**: 値の順位を ` .:-=+*#%@`（低→高）で表す。`_` 取引なし、`B` 破産、`S` ロスカット、`?` 計算不能、`x` 自身のスコアは正常だが近傍のせいで Robust Score が −∞、`R` 島の中、`P` 孤立した P4 合格点。行が 2 番目の軸（上が大きい値）、列が 1 番目の軸
- **島の面積 1**: 面積 1 の島は `parameter_region` に保存せず、候補の `region_status = ISOLATED_PASS` で表す
- **入力**: フィルタ実行が使ったジョブの `pass_result` と、そのジョブの日次 Parquet（P3 で保存済み）を読む。新しい市場データは読まない
- **テストで確かめた 3 点（承認時の確認事項）**:
  1. 合格 0 件でも全候補に評価値が保存される: `test_no_filter_pass_still_evaluates_everyone`（合成）、`test_every_candidate_is_evaluated_and_minus_inf_causes_are_kept`（偽の端末のラウンド、DB まで）
  2. 破産と取引なしが別々に記録され、近傍の件数が一致する: `test_minus_inf_causes_are_kept_and_counted`（全セルで直接数えた件数と一致）と、同じ結合テスト（`BANKRUPTCY 1・NO_TRADES 6・OK 2`）
  3. 合成データで台地が孤立ピークより高く評価され、島の中心が仕様どおり: `test_isolated_peak_scores_below_the_plateau`（素のスコアは針 0.20 ＞ 台地の中心 0.10 だが、Robust Score は針 0.01 ＜ 中心 0.08。島は台地の 9 点で、メドイドは中心）、`test_medoid_rules_l_shape_and_ties`（同点の規則）
- テスト: 226 件（P5 で 18 件追加）
